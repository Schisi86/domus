# Sicherheit und Datenschutz

## Was ist implementiert

| Bereich | Umsetzung |
|---|---|
| Transportverschlüsselung | TLS 1.2/1.3 (rustls) für HTTP und WebSocket. Ohne eigenes Zertifikat erzeugt der Server beim ersten Start ein selbst signiertes und behält es. |
| Zertifikatsprüfung im Client | Pinning des SHA-256-Fingerabdrucks („Trust on first use“). Unbekannte Zertifikate werden mit Fingerabdruck angezeigt und müssen bestätigt werden; ein **geändertes** Zertifikat blockiert die Verbindung mit deutlicher Warnung. Öffentlich vertrauenswürdige Zertifikate (z. B. Let's Encrypt) werden ohne Rückfrage akzeptiert. Einladungslinks enthalten den Fingerabdruck. |
| Medien | WebRTC mit DTLS-SRTP zwischen den Clients (auch über TURN verschlüsselt). |
| Passwörter | Argon2id (Standardparameter der `argon2`-Crate), individuelles Salt, nie im Klartext gespeichert oder protokolliert. Konstante Fehlermeldung und Dummy-Hash bei unbekannten Benutzern (kein Benutzer-Enumeration über Antwortzeiten/Text). |
| Sitzungen | 256-Bit-Zufallstoken; in der DB nur SHA-256-Hash. Ablauf nach 30 Tagen Inaktivität (konfigurierbar). Passwortänderung beendet alle anderen Sitzungen, Sperre beendet alle. |
| Token-Speicherung im Client | Windows: DPAPI (an das Windows-Benutzerkonto gebunden). macOS: AES-256-GCM mit einem zufälligen Schlüssel, der im Anmelde-Schlüsselbund des Benutzers liegt. Android: im privaten App-Ordner, den nur Domus lesen kann (ohne zusätzliche Verschlüsselung, siehe unten). Passwörter werden im Client nicht gespeichert. |
| Berechtigungen | Ausschließlich serverseitig geprüft (`perms.rs`, jede Operation). UI blendet nur aus. Rollenhierarchie verhindert Rechteausweitung (man kann nur Rollen unterhalb der eigenen verwalten und keine Rechte vergeben, die man selbst nicht hat). Fremde DMs sind auch für Administratoren unsichtbar. |
| Eingabevalidierung | Längenlimits, Steuerzeichen-Filter, Namensregeln, typisierte JSON-Deserialisierung; FTS-Suchbegriffe werden quotiert (keine Such-Injection); SQL nur parametrisiert. |
| Dateien | Gespeichert unter Zufalls-IDs (kein Pfad aus Benutzereingaben), Dateinamen nur zur Anzeige und bereinigt. Größenlimit wird beim Streamen erzwungen, Speicherkontingent, Abbruch löscht Teildateien. Auslieferung mit `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`, `Content-Disposition: attachment` (Bilder: inline, nur bei erkannter Signatur PNG/JPEG/GIF/WebP). Dateien werden nie ausgeführt. Uploads sind abschaltbar. Download nur mit Leserecht auf den Kanal. |
| Rate-Limits | Anmeldung/Registrierung pro IP (6/min, Burst 10), WebSocket-Operationen pro Verbindung (10/s, Burst 40), Nachrichten (2/s, Burst 10), Verbindungen gesamt/pro IP, maximale Framegröße 128 KB, begrenzte Ausgangswarteschlange (langsame Clients werden getrennt). |
| Stabilität | Jede Verbindung läuft in einem eigenen Task; Fehler/Panics betreffen nur diese Verbindung (Release-Build ohne `panic=abort`). Ungültiges JSON, Übergrößen oder Flooding trennen nur den Verursacher. |
| Sichere Standardkonfiguration | Bind an `127.0.0.1`, TLS an, Registrierung „nur mit Einladung“, Owner-Einrichtung über Einmalcode, TURN aus. Freigabe ins Netzwerk erfordert eine bestätigte Warnung mit Port-Erklärung. |
| Protokollierung | Sicherheitsrelevante Ereignisse (Fehlanmeldungen mit IP, Anmeldungen, Registrierungen, Sperren, Rollen-/Kanaländerungen, Löschungen durch Moderatoren, Backups) im Serverlog bzw. Audit-Protokoll. Keine Nachrichteninhalte, keine Passwörter/Token. Logrotation (7 Tage Standard). |
| Datenlöschung | Benutzer können ihr Konto löschen (optional inkl. aller Nachrichten). Aufbewahrungsfrist für Nachrichten konfigurierbar. Nicht verwendete Uploads werden nach 1 h gelöscht. |
| Medienzugriff | Mikrofon nur während einer Sprachsitzung, Kamera und Bildschirm nur nach ausdrücklicher Aktion; Bildschirmübertragung wird permanent angezeigt und ist jederzeit beendbar; Systemdialog für die Quellenauswahl. |

## Was NICHT implementiert ist (ehrliche Einschränkungen)

* **Ende-zu-Ende-Verschlüsselung nur für Direktnachrichten und nur, wenn sie für die Unterhaltung eingeschaltet ist (ab 0.10.0, siehe unten).** Kanalnachrichten, nicht verschlüsselte DMs und alle Dateien kann der Serverbetreiber in der Datenbank bzw. im Upload-Ordner lesen. (Audio/Video/Bildschirm sind zwischen den Clients per DTLS-SRTP verschlüsselt; der Server sieht sie nicht.)
* **Kein Verschlüsseln der Datenbank im Ruhezustand.** Schutz über Dateisystemrechte/Festplattenverschlüsselung des Server-PCs.
* **Durchsetzung von Sprech-/Video-/Bildschirmrechten in P2P-Sitzungen**: Der Server verweigert die entsprechenden Zustände (`voice.update`) und markiert stumme Benutzer; ehrliche Clients rendern nur vom Server freigegebene Streams. Ein manipulierter Client könnte dennoch Medien an andere Teilnehmer senden, weil diese nicht über den Server laufen. Vollständige Durchsetzung erfordert eine SFU (geplant).
* Keine Zwei-Faktor-Anmeldung, keine Passwort-Zurücksetzung per E-Mail (bewusst keine externen Dienste; Admin kann Konto löschen, Benutzer neu registrieren).
* Kein Virenscan hochgeladener Dateien.
* **Internet-Tunnel (ab 0.5.0):** Für Einladungen über das Internet läuft der Verkehr über das öffentliche Relay `bore.pub` (Dritter). Inhalte bleiben TLS-verschlüsselt und per Fingerabdruck geprüft; das Relay sieht IP-Adressen, Zeitpunkte und Datenmengen. Der Relay-Port ist öffentlich erreichbar, Schutz bietet die Einladungspflicht. Hinter dem Tunnel sieht der Server alle Teilnehmer als `127.0.0.1`: das Verbindungslimit pro IP entfällt dort, die Login-Bremse gilt gemeinsam. Der Tunnel ist im Verbindungs-Check abschaltbar.
* **TURN über den Tunnel (ab 0.6.0):** Freigegebene Server in der Desktop-App schalten den TURN-Relay ein (UDP lokal, TCP auch über bore.pub). Zugangsdaten sind zeitlich begrenzt (12 h, HMAC mit Server-Geheimnis) und gehen nur an angemeldete Benutzer. Medien bleiben DTLS-SRTP-verschlüsselt; der Relay leitet nur weiter.
* **Moderation (ab 0.6.0):** Auszeit, Kicken, serverseitiges Stummschalten und Verschieben werden ausschließlich serverseitig durchgesetzt (Rechte + Rangfolge, Inhaber unantastbar) und im Audit-Protokoll vermerkt. Eine Auszeit entzieht Schreib-, Datei-, Sprech-, Kamera- und Bildschirmrechte in Serverkanälen; DMs bleiben nutzbar. Serverseitiges Stummschalten ist wie die übrigen Sprechrechte „honest client“: Der Server markiert und verweigert, ein manipulierter Client könnte trotzdem Medien direkt an andere senden (siehe SFU-Hinweis oben).
* **Profile (ab 0.7.0):** Banner-Farben werden serverseitig streng geprüft (nur `#rrggbb`, höchstens zwei), „Über mich“ ist auf 190 Zeichen begrenzt und wird als Text, nicht als HTML angezeigt.
* **Sprachnachrichten (ab 0.7.0):** werden wie andere Dateien gespeichert (Größenlimit, Leserecht nötig). Als Audio gilt eine Datei nur bei passender Signatur; WebM nur mit Endung `.weba`/`.opus`.
* **„Für später“ und Notizen** liegen nur lokal auf dem Gerät, nicht auf dem Server.
* **Ende-zu-Ende-verschlüsselte Direktnachrichten (ab 0.10.0):** Jedes Gerät erzeugt ein ECDH-Schlüsselpaar (P-256). Der private Schlüssel bleibt auf dem Gerät (Desktop-App: mit Windows-DPAPI an das Benutzerkonto gebunden, `secrets.json`), der Server verteilt nur öffentliche Schlüssel. Aus eigenem privatem und fremdem öffentlichem Schlüssel wird per HKDF ein AES-256-GCM-Schlüssel abgeleitet; der Server speichert und vermittelt nur das Chiffrat. **Grenzen:** (1) Die Schlüssel sind langlebig – keine Forward Secrecy; wer später einen privaten Schlüssel erbeutet, liest auch alte Nachrichten. (2) Der Server könnte einen falschen öffentlichen Schlüssel ausgeben; dagegen hilft nur der Vergleich der Sicherheitsnummer auf anderem Weg. Ein Schlüsselwechsel wird angezeigt, aber nicht verhindert. (3) Anhänge, Umfragen, Reaktionen und Metadaten (wer wann mit wem, Nachrichtenlänge) sind nicht verschlüsselt. (4) Lesbar nur auf Geräten mit passendem privatem Schlüssel; für ein weiteres Gerät gibt es die kennwortgeschützte Schlüsselsicherung (PBKDF2-SHA-256, 310 000 Runden, AES-GCM). (5) Im Browser-Build liegt der private Schlüssel ungeschützt im `localStorage`. (6) Die Kryptografie nutzt WebCrypto, wurde aber nicht extern geprüft.
* **Direktversand (ab 0.10.0):** Dateien laufen über einen WebRTC-Datenkanal (DTLS) direkt zwischen zwei Clients, bei Bedarf über den TURN-Relay, der nur verschlüsselte Pakete sieht. Der Server vermittelt den Verbindungsaufbau (höchstens 64 KB je Signal, nicht an blockierte oder Offline-Benutzer) und speichert nichts. Der Empfänger muss jede Datei annehmen und wählt den Speicherort; Dateinamen werden von Pfad- und Steuerzeichen befreit. Es gibt keinen Virenscan – nur Dateien von vertrauten Personen annehmen.
* **Zeichnen, Clips, Gemeinsam schauen (ab 0.10.0):** Markierungen und Wiedergabe-Befehle laufen über den Datenkanal des Anrufs und werden auf Empfängerseite begrenzt und geprüft. Clips entstehen nur lokal; wer Stimmen mit aufnimmt, löst bei den anderen einen Hinweis aus – ein manipulierter Client könnte ihn unterdrücken (und ohnehin mitschneiden). „Gemeinsam schauen“ lädt Inhalte von YouTube (`youtube-nocookie.com`) bzw. der angegebenen Adresse; diese Anbieter sehen dabei die IP-Adresse jedes Zuschauers.
* **Profil per QR-Code übertragen (ab 1.0.1):** Das sendende Gerät holt sich von jedem verbundenen Server einen **Einmal-Code** (20 Zeichen aus 32, ≈100 Bit, 3 Minuten gültig, nur einmal einlösbar, ein neuer Code macht den alten ungültig, nur im Arbeitsspeicher des Servers). Der QR-Code enthält Servername, Benutzername, erreichbare Adressen, den Zertifikats-Fingerabdruck und diesen Code – **keine Sitzungstoken und keine Passwörter**. Das empfangende Gerät löst den Code bei `POST /api/v1/auth/link` ein (Anmelde-Bremse wie beim Login) und bekommt eine **eigene neue Sitzung**, die einzeln abgemeldet werden kann. Das Zertifikat wird mit dem Fingerabdruck aus dem QR-Code geprüft; ein abweichendes Zertifikat wird nicht akzeptiert. Alle angemeldeten Geräte erhalten den Hinweis „Neues Gerät angemeldet“. **Risiko:** Wer den QR-Code oder den kopierten Text innerhalb der 3 Minuten abfotografiert oder abfängt, kann sich einmalig als du anmelden – Code nur dir selbst zeigen, den Text nicht über fremde Kanäle schicken; im Zweifel unter Einstellungen › Geräte abmelden. Private Schlüssel für verschlüsselte DMs werden nicht übertragen (dafür gibt es die Schlüsselsicherung).
* **Angemeldete Geräte (ab 1.0.1):** Einstellungen › Geräte listet die Sitzungen des eigenen Kontos (Gerätename, seit wann, zuletzt aktiv; die Kennung ist nur ein Präfix des Token-Hashs). Andere Geräte lassen sich abmelden – ihre Verbindung wird sofort getrennt, die übrigen bleiben verbunden. Das eigene Gerät meldet man über „Abmelden“ ab.
* **Android-App (ab 1.0.1):** in 1.0.1 ein reiner Client; ab 1.0.2 kann sie auch Server hosten und den Bildschirm teilen (siehe unten). Sitzungstoken und der private E2E-Schlüssel liegen im privaten App-Ordner (`/data/data/org.domus.app`), den Android anderen Apps verweigert – sie sind dort aber **nicht zusätzlich verschlüsselt** (kein Android-Keystore); auf gerooteten Geräten oder über ein Backup mit Zugriff auf App-Daten wären sie lesbar. Netzwerkverkehr läuft wie auf dem Desktop über Rust mit TLS-Pinning, nicht über das Android-WebView. Das APK ist mit einem eigenen Schlüssel signiert, wird aber nicht über den Play Store verteilt (Installation aus „unbekannten Quellen“ nötig).
* **Server auf dem Handy (ab 1.0.2):** Der Server läuft im App-Prozess mit denselben Voreinstellungen wie am PC (TLS, Einladungspflicht). Datenbank, Zertifikat und Uploads liegen im privaten App-Ordner – **eine Deinstallation löscht den Server samt allen Nachrichten** (vorher Backup ziehen). Wird er „im Netzwerk erreichbar“ gemacht, ist er im jeweiligen WLAN bzw. über den Tunnel erreichbar; öffentliche WLANs sind dafür ungeeignet. Ein Vordergrund-Dienst mit dauerhafter Benachrichtigung zeigt an, dass er läuft.
* **Bildschirm teilen am Handy (ab 1.0.2):** Nur nach dem Android-Dialog „Aufnahme starten“; Android zeigt die Aufnahme selbst an (Statusleiste) und kann sie jederzeit beenden. Die Bilder gehen nur als Videospur in den laufenden Anruf (DTLS-SRTP), werden nicht gespeichert und nicht an den Server geschickt. **Achtung:** Geteilt wird alles auf dem Bildschirm, auch Benachrichtigungen anderer Apps.
* **Chats löschen und Lesebestätigungen (ab 1.0.2):** „Chat löschen“ blendet den Verlauf nur für dich aus; die Nachrichten bleiben auf dem Server und bei der anderen Person (echtes Löschen eigener Nachrichten geht weiterhin einzeln). Lesebestätigungen werden nur ausgetauscht, wenn beide sie eingeschaltet haben; sie verraten, wann du eine Direktnachricht geöffnet hast.
* **macOS (ab 1.0.2):** Die App ist nur ad hoc signiert und nicht von Apple notarisiert; Gatekeeper warnt deshalb beim ersten Start. Prüfe im Zweifel die SHA-256-Prüfsumme der `.dmg`. Hardened Runtime ist nicht aktiv (erfordert eine Developer-ID-Signatur).
* **Name (ab 1.0.0):** Domus hieß vorher NexUs bzw. NexusTalk. Die Windows-Firewall-Regel heißt jetzt „Domus Server“ und gilt für `Domus.exe`; alte Regeln für `nexustalk.exe` bleiben bestehen, bis man sie in der Windows-Firewall löscht.
* **Fernsteuerung (ab 0.9.0, überarbeitet in 0.10.0):** Nur in der Desktop-App und nur, wenn der **gesamte Bildschirm** geteilt wird (nicht ein einzelnes Fenster), damit der Steuernde sieht, was er bedient. Eingaben werden lokal per Windows `SendInput` eingespielt und nur, solange eine ausdrücklich freigegebene Sitzung läuft: Der Host hat die Funktion eingeschaltet und entweder stimmte das Passwort des Betrachters (fünf Fehlversuche sperren ihn fünf Minuten) oder der Host hat die einzelne Anfrage bestätigt. Das Passwort wird mit DPAPI geschützt gespeichert. Die Umschalt-Taste (Standard F8) beendet die Steuerung beim Host sofort; beim Ende werden alle noch gehaltenen Tasten und Maustasten losgelassen. Der Host sieht ein deutliches Banner und kann sofort widerrufen; das Beenden der Bildschirmübertragung schaltet die Steuerung ab. Steuerbefehle laufen Ende-zu-Ende über den WebRTC-Datenkanal (nicht über den Server). Risiko bleibt: Wer die Steuerung übernimmt, kann den geteilten Rechner bedienen – nur an vertraute Personen vergeben und ein starkes Passwort wählen.
* **Selbst-DM „Notizen“ (ab 0.9.0):** gespeicherte Nachrichten liegen als normale Direktnachricht an dich selbst auf dem Server (keine Ende-zu-Ende-Verschlüsselung, wie bei allen Texten).
* **Öffentliche STUN-Server:** Für Sprache/Video fragen Clients zusätzlich `stun.cloudflare.com` und `stun.l.google.com` nach ihrer öffentlichen Adresse. Diese Dienste sehen dabei die IP-Adresse, aber keine Medien.

## Welche Daten speichert der Server?

| Daten | Zweck | Sichtbar für |
|---|---|---|
| Benutzername, Anzeigename, Avatar, Statusmeldung | Profil | alle Mitglieder |
| Passwort-Hash (Argon2id) | Anmeldung | niemand (nur Server) |
| Sitzungen: Token-Hash, Zeitpunkte, Gerätename | Anmeldung | nur Server |
| Rollen, Online-Status (bzw. „offline“ bei unsichtbar) | Rechte/Präsenz | alle Mitglieder |
| Nachrichten, Antworten, Erwähnungen, Bearbeitungszeit | Chat | Benutzer mit Leserecht auf den Kanal; DMs nur die beiden Teilnehmer |
| Dateien (Name, Größe, Typ, Inhalt) | Anhänge | Benutzer mit Leserecht auf den Kanal |
| Lesestatus pro Kanal | Ungelesen-Markierungen | nur der Benutzer selbst |
| Freundes-/Blockierliste | Kontakte | nur die beteiligten Benutzer (Blockierungen sind für die blockierte Person nicht direkt sichtbar) |
| Sprachkanal-Teilnahme, Stumm/Ton aus/Kamera/Bildschirm | Anzeige | Benutzer mit Leserecht auf den Kanal |
| Audit-Protokoll (Aktion, Akteur, Ziel) | Moderation | Rolle mit „Audit-Protokoll“ |
| Serverlog: Zeit, Ereignis, bei Fehlanmeldung IP + Benutzername | Sicherheit | Serverbetreiber |

**IP-Adressen**: werden nicht in der Datenbank gespeichert, nur im rotierenden Serverlog bei Anmeldungen/Fehlversuchen. In P2P-Sprachsitzungen sehen die Teilnehmer gegenseitig ihre (öffentlichen bzw. lokalen) IP-Adressen – das ist bei direkten WebRTC-Verbindungen technisch unvermeidbar. Wer das nicht möchte, kann über einen TURN-Relay gehen (zukünftige Option „nur Relay“).
